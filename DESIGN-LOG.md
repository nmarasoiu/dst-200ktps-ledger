# Design log

Every decision in the [design notes](README.md) that was later corrected or rescoped, what was wrong with it, and how the flaw was found. Most were found by one of four methods: re-reading the design against its own invariants, walking a concrete failure scenario step by step, checking a claim against its cited source, or reading the dependency's source code.

Entries carry no commit or pull request links: pull requests are merged by rebase, which gives every commit a new hash, so a link written on a branch breaks once merged. To find the change behind an entry, search the history for a phrase of the decision, for example `git log -S "<phrase>" -- README.md DESIGN-LOG.md`; GitHub shows the pull request of each commit.

| # | Before | After | How the flaw was found |
| --- | --- | --- | --- |
| 1 | Postgres as the hub, with CDC to TigerBeetle and back | Kafka as the intent log, TigerBeetle as the outcome store, Postgres as an async projection | Throughput arithmetic: one Postgres writer doing several writes per transaction at 200k TPS, with CDC slot lag able to stall the database |
| 2 | A Kafka Streams stage assigning time-ordered IDs, with 1 to 2 TB per day of dedupe state | The edge hashes the client key into the TigerBeetle ID; no ID stage and no state store | Cost of the state store and its restore time after failover, against a documented 10% throughput cost of random IDs |
| 3 | Crash table and next steps still describing the removed ID stage | Rewritten for hashed IDs | Re-reading the whole document for consistency after the change |
| 4 | TigerBeetle "100k to 500k TPS" and in-batch ordering marked *verified* | Downgraded to *verify* | Opening the cited pages: neither states it |
| 5 | The batcher silently dropped commands past their deadline, voids included | Late authorizations get an outcome; voids are never expired | Checking the batcher against the invariant "every request reaches exactly one terminal outcome", and asking what happens to a late void |
| 6 | Results written in a Kafka transaction, offsets committed afterwards | Offsets committed inside the same transaction | Reading the batcher step by step against Kafka's transactional API |
| 7 | Kafka Streams facts (standby replicas, commit interval) after Kafka Streams was dropped | Removed, and the latency budget restated in terms of the actual stages | Re-reading the facts table against the current architecture |
| 8 | Can an authorization and its void share a key, given their idempotency keys differ? | Three keys with three jobs: the client key, the TigerBeetle ID (per command) and the Kafka record key (per hold). The submission topic must be delete-only, with a fixed partition count | A design question about ordering; separating idempotency from routing exposed the compaction and repartitioning hazards |
| 9 | Ordered voids: same partition, same producer, void written only after the authorization's send completes | Fenced cancels: write a fence transfer with the authorization's own ID, then void | Walking the edge-crash scenario: a crashed edge's stale send can reach Kafka after a cancel sent through another edge instance, and the void then burns its ID |
| 10 | A ledger-side sweeper for orphaned holds | The caller cancels on any non-definitive result, like an acquirer's timeout reversal | The ledger cannot tell a lost reply from a delivered one, so a sweeper would void holds the caller believes approved |
| 11 | Expiry decided by the batcher's clock | Expiry writes the fence, so the ledger decides | Walking a batcher crash: submit at 1.1 s, crash before commit, replay at 1.3 s reports "expired" while the funds are held |
| 12 | Hedged submission rejected because it breaks void ordering | Safe with fenced cancels; deferred only for the extra TigerBeetle load | Follows from #9 |
| 13 | Fence behavior assumed from documentation and memory | Verified in TigerBeetle's source: the ID check runs first, flags are compared first, zero-amount transfers are allowed. The fence and the void must not be linked, and no lookup is needed to recognize a fence | Reading `create_transfer`, `create_transfer_exists` and `post_or_void_pending_transfer` in the TigerBeetle source |
| 14 | Separate `expired` and `cancelled` outcomes for a fenced authorization | One outcome, `not_executed` | Re-reading against the invariants: a retried copy of an expired authorization would find the fence and be reported `cancelled`, giving one request two outcomes |
| 15 | Correctness after a rebalance credited to Kafka's transactional fencing and TigerBeetle idempotency | Kafka's fencing stops only a zombie batcher's Kafka writes; the fence makes its TigerBeetle calls harmless. Added to the crash table | Listing every actor that can create `A` against every actor that decides `A` must never exist |
| 16 | Stand-in exception: the caller must not cancel after a stand-in | No exception: the timed-out authorization is always cancelled, and the stand-in is a new forced hold with its own ID | The edge cancels on its own timeout anyway; and if neither cancels and `A` went through, `A`'s hold and the forced hold hold the money twice |
| 17 | Network reversals routed through a lookup from network identifiers to `A` | The client key is derived from identifiers the reversal echoes, so `A` is computed directly | The lookup needs the authorization's result to be visible first, which brings back the ordering race the fence removed |
| 18 | `exists` treated like `ok`, with the original result rebuilt by a lookup | `ok` is now `created`, and `exists` returns the original timestamp, so no lookup is needed | Checking the facts table against TigerBeetle's current source and its 0.17.0 API changes page |
| 19 | A fence's `exists` results not told apart | Only `exists_with_different_flags` means the authorization holds `A`; any other `exists` result means an earlier fence holds it | Walking a cancel's fence meeting an earlier expiry fence while explaining fencing step by step |
| 20 | Expiry lag of a second or two, from a practitioner report | About 100 ms: the primary injects an expiry pulse after a commit, or every 100 ms when idle, expiring up to 8,189 holds per pulse | Reading `pulse_timeout` and `commit_execute` in TigerBeetle's replica |
| 21 | CDC options unknown; auto-expired holds assumed invisible without a scan | Built-in CDC reports them as `two_phase_expired`, but only over AMQP | Reading TigerBeetle's CDC docs and source |
| 22 | Kafka's fencing of a zombie batcher's transaction taken as given | It holds only when offsets carry the consumer's live group metadata; fs2-kafka sends it | Reading Kafka's group coordinator (`validateOffsetCommit`) and fs2-kafka's producer |
| 23 | A replayed cancel repeats its result codes | It repeats its outcome; the void's code can change, because a void that failed with a transient error burns `V` | Walking each row of the fence table through TigerBeetle's source a second time, as a replay |
| 24 | "TigerBeetle is not the bottleneck" stated as settled | The premise to measure first, with the built-in benchmark; a third-party run leveled off near 107k TPS, and each authorization costs about two TigerBeetle events over its life | Looking for a source for the throughput figure and counting events per authorization |
| 25 | A caller could resend an authorization with the same key after a timeout and get the original outcome | After a non-definitive result the caller only cancels, until acknowledged; the acknowledgement is final and a new attempt uses a new key. Consumers never let a later approved override a cancel | Checking whether `exists` reflects the hold's state: a voided authorization still returns `exists`, and a resend landing just before the edge's cancel is approved and then voided |
| 26 | Postgres projection fed by TigerBeetle change data capture | Fed by the results topic, with expiries derived from each hold's timestamp and timeout; the pipeline is TigerBeetle's only writer, and CDC is an optional audit feed | Asking how CDC would reach Kafka: it speaks only AMQP, while the results topic already records every change except expiries, which follow from what it records |
| 27 | A 200k TPS target, with TigerBeetle's single-cluster throughput the premise to measure first in stage 0 | 50k TPS, 75k under stress, or about 100k TigerBeetle events per second; one cluster is assumed to carry it, and stage 7 measures the whole pipeline | A scope decision rather than a flaw: the project's subject is crash safety and deterministic simulation, and measuring TigerBeetle's ceiling needs target-class hardware. TigerBeetle's homepage claims 100k to 500k TPS, so the load sits at the low end of that range |
| 28 | Core scope of authorization and cancel; capture left to phase A, so every approved hold ended in a cancel or an expiry | One full or partial capture per hold joins the core: a post with the fixed ID `P = hash(A, "post")`, never fenced or expired, resent until answered. Holds time out after 7 days, stamped by the edge | Counting TigerBeetle events per authorization for the 50k target: without captures, a load test's second event is an expiry days later, and the domain types and cancel outcomes would change once capture arrived |
| 29 | Authorization outcomes `approved`, `rejected` and `not_executed`, with "exactly one terminal outcome" checked over them | Outcomes are decisions, approved or declined; the reason, `not_executed` included, is best-effort detail | Walking a duplicate of a declined authorization after a cancel's fence: it comes back `not_executed`, a false alarm for an invariant over outcomes |
| 30 | Seven invariants checked in every layer, the throughput floor among them | Safety invariants that hold at every point under any faults and clock skew, and liveness and timeliness properties checked once faults stop. "Exactly one terminal outcome" becomes "never two different outcomes" plus "eventually one", and the 1.5 s edge deadline becomes a property | Checking what each invariant needs as input: the throughput floor needs load and time, not just a history, and no invariant checked the deadline the design is built around |
| 31 | The offline checker reads the topics and TigerBeetle; the load generator arrives in stage 7 | The history includes what each caller was told. A workload driver that follows the caller's contracts records it from stage 6, and stage 7 steps its rate | The same check: "the edge's reply matches the ledger" and "a cancel reported `cancelled`" are about what the caller was told, which no topic records |
| 32 | Contract tests in stage 4, after the simulator; the TigerBeetle client wrapper in stage 5 | Each port's contract suite is written before its simulated adapter and runs alongside stage 3. The real TigerBeetle adapter moves to stage 4, so its suite tests the adapter the shell will use | Reading sections 11 and 14 side by side: one put contract tests on day one, the other after the simulator; and a suite run against both adapters of a port needs the real adapter to exist |
| 33 | Admission control specified in stage 1 | A stage 2 state machine, with the throughput floor as its property | Stage 1 is done when invariants fail on bad histories, and admission control has no safety invariant to fail |
| 34 | The batcher writes results, replies and offsets in one Kafka transaction, and readers consume read-committed | No Kafka transactions. Results and replies are written at least once, offsets are committed after both are acknowledged, and consumers keep one decision per request | Asking what the transaction protects. Not the TigerBeetle call, and not consumers from duplicates, which already enter before the batcher; replays never change a decision. Reading Kafka's `lastStableOffset` showed the cost: one stalled batcher's open transaction holds back every edge's replies on the partitions it wrote, for up to the 60 s default timeout |
| 35 | A Kafka pipeline: the edge writes a submission topic, a batcher calls TigerBeetle and writes results and replies topics, and every edge reads the replies to find its own | The logged direct path: the edge logs the command, calls TigerBeetle, logs the outcome and answers on its own connection. A reconciler gives an outcome to every command an edge left without one. No replies topic and no reply routing | Right-sizing the whole path. Reply routing existed only because the process holding the connection was not the one calling the ledger, and the batcher's place on the main path cost a poll, a call and two writes per answer. A direct path that journals to a local disk was rejected first, because a local disk is lost with its machine |
| 36 | Log intent before effect; what the caller was told is recorded by no topic | Also log outcome before answer: every decision is acknowledged by the in-sync replicas before the caller hears it, and the edge waits without blocking a thread. Requests the edge refuses before their command is acknowledged are definitive, because only the edge submits an authorization | Asking what an outcome written without waiting would lose: the reconciler can rebuild the decision from the ledger, but not the reason or what the caller was told. Reading `checkEnoughReplicasReachOffset` showed what an acknowledgement means: every in-sync replica has the write |
| 37 | Recovery is the normal path: a replay runs the same code as normal processing | Recovery uses the normal rules on a second path: the reconciler applies the edge's rules and the fence, and the simulator crashes edges between every pair of steps so that path runs constantly | Follows from #35. A second path that rarely runs in production is the weakness section 13 held against a sync path with a sweeper, so it has to run constantly in the simulator instead |
| 38 | Two deadlines: a core deadline of 1.2 s, checked by the batcher on another machine, and the edge's 1.5 s | One deadline, the edge's. The reconciler acts a grace period after it, and clock skew changes only how soon | Follows from #35: the core deadline existed so that the batcher could fence late authorizations before submitting them |
| 39 | Stage 8: chaos in a Kubernetes staging cluster | Kills, pauses and network faults run in Docker Compose in stage 6; Kubernetes chaos moves to roadmap phase G | Asking what a staging cluster adds beyond stage 6: deployment behavior, not the protocol. Pausing a container and resuming it after it was replaced reproduces the zombie rows directly |
| 40 | Stage 7 steps the driver to 50k and 75k TPS | Stage 7 finds where useful throughput levels off and which component sets that point, on the hardware at hand | The same reason as #27: hitting 50k end to end needs the same target-class hardware as measuring TigerBeetle alone |
| 41 | TigerBeetle change data capture, through RabbitMQ or Redpanda Connect, as the optional audit feed; Postgres as a projection for queries | A tailer reads every transfer by timestamp through the Java client, for the offline checker and the audit. Postgres becomes the complete audit log in phase E, loading the command log and the tailer exactly once by storing each reader's position in the same transaction as its rows | Reading `get_scan_from_query_filter` and the timestamp assertions in `create_transfer`: a timestamp-only query is valid, and timestamps only grow. That the audit must hold every command and answer, not only the ledger's part, is a scope decision |
| 42 | The component that gives unfinished commands an outcome is called the reconciler | It is called the resolver. Reconciliation keeps its banking meaning, comparing two records, which the offline checker and the audit log do | Asking what the reconciler and the tailer are for: in banking, reconciliation compares two records, such as the ledger against the network's settlement, and this component compares nothing |
| 43 | A command is a straggler a grace period after the deadline the edge stamps into it, by the resolver's clock | Judged in log time: once the resolver has read a record appended the deadline plus the grace period after the command, or has reached the end of an idle partition that long after it. The edge stamps no deadline | Asking how the resolver tells a missing outcome from one not yet read: after a restart, every command it reads again is past its deadline by the clock, so it would fence commands whose outcomes were a few records ahead, in a burst on the ledger every edge shares |
| 44 | The edge may refuse only before the command is acknowledged; after that it calls TigerBeetle however little time is left | It may refuse until it hands the authorization to the TigerBeetle client. Each step has a budget, a partition without a leader is refused at once, and the producer's delivery timeout sits near the deadline | Counting what a timeout costs against a refusal: two cancels and usually a fence, against at most one fence. Reading the producer's defaults showed records retried for 120 s in one shared buffer, and the TigerBeetle client's queue showed that an event cannot be taken back once handed over |
| 45 | Each consumer keeps one decision per command, prefers a specific reason and never lets an approval override a cancel, in its own code | One merge function in the core, shared by every reader. Its result does not depend on order or duplicates, which property tests check | Asking whether every reader combines outcomes the same way in any order: the rules were spread over three places in the README, and each consumer would have written them again |
| 46 | A fence records why `A` was fenced, so an expiry fence and a cancel's fence differ, and any `exists_with_different_*` code on a fence is read as an earlier fence | Every fence is identical and fixed for all time, and the reason is in the log. On a fence, an `exists_with_different_*` code other than `_flags` is unexpected and raises an alarm | Asking why two fences of one ID should differ: the log already records why, and reading every unexpected code as an earlier fence would hide a change to the fence's fields |
| 47 | The offline checker reads TigerBeetle through a tailer that runs alongside the pipeline from stage 6 | It runs one scan of every transfer after each run. The tailer, the same scan run continuously, arrives with the audit log in phase E | Asking what the tailer is for: the checker needs the ledger only once a run ends, and if queries go through consensus, a tailer running during a run takes capacity from the requests under test and skews stage 7 |
| 48 | A refusal is definitive, and the caller may retry a refused request with a new key. The invariant: a refused request never creates a hold | A refusal speaks only for the copy it refused. The caller resends it with the same key, as after an HTTP 503, which either is the first real attempt or finds the copy that reached TigerBeetle. No hop between the caller and the edge may retry an authorization on its own. The invariant: if a caller stopped resending after a refusal, no hold was ever created for its key | Walking a lost answer followed by a retry from a hop the caller does not see: the first copy creates the hold, the retry is refused, and the caller, told "refused", moves on with a new key, so the money is held twice. Every other decision is ordered by TigerBeetle; a refusal is made at the edge, and only the same key lets TigerBeetle answer for every copy |
| 49 | `A = hash(clientId, clientKey)`, with the client ID never defined | `A = hash(clientKey)`. A deployment serves one client, the bank, and another client gets its own deployment. Client keys share one key space and must be unique within it for all time | Asking where the client ID comes from. If it ever changed, cancels would compute the wrong `A` and report `cancelled` while the hold survived; and if it came from the sender's login, a capture sent by the clearing system rather than the authorization system would compute a different `A`. A scope decision removes the question |
| 50 | Command log retention and the resolver's restart point left unset, so Kafka's defaults applied: 7 days, and a consumer that skips to the end of the log. Postgres the complete audit log, with no rule for when it is complete | Kafka is transport, kept 30 days; TigerBeetle is the permanent record of money, and Postgres the long-term record of commands and decisions, under EU rules. The resolver resets with `none`. A period closes once the audit log holds everything in it, with money placed by TigerBeetle's clock and decisions by the log's append time | Asking whether Postgres lag at a month end could leave a report incomplete, and whether Kafka should then be the permanent record. The record is durable before the answer whatever the retention; completeness at a cut-off needs a close rule, not speed. Reading Kafka's defaults showed the 7-day retention and the reset to the end of the log |
